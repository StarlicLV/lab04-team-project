## 2. Особистий внесок
Уся моя робота зосереджена в одному файлі `routes/shop.py`. Шаблони сторінок вбудовано в цей файл, тому спільні файли команди я не змінював, окрім мінімальної заміни endpoint меню.

### 2.1. Публічне меню (`shop.menu`, адреса `/menu`)
- Маршрут меню перенесено з `app.py` у `routes/shop.py`, його endpoint тепер `shop.menu`. Дані зі словника в `app.py` більше не використовуються.
- Товари читаються з БД запитом `SELECT * FROM products WHERE is_available = 1`, тому вимкнені товари клієнти не бачать.
- Товари групуються за полем `category`; кожен товар показано карткою з назвою, описом і ціною.
- Кнопка «Додати в кошик» — це форма з методом POST на endpoint `cart.add_to_cart` (узгоджено з частиною А).
- У шаблонах використано класи `dark:`, щоб сторінка коректно виглядала в темній темі, а також адаптивну сітку (1, 2 або 3 колонки залежно від ширини екрана).

### 2.2. Пошук і фільтрація (рівень 3)
- **Пошук за назвою** — параметр GET `?q=`. Запит: `... AND name LIKE ?` із параметром `'%' + q + '%'`.
- **Фільтр за категорією** — параметр GET `?category=`. Запит: `... AND category = ?`.
- Обидва фільтри можна поєднувати: SQL-запит збирається динамічно, до `WHERE` додаються лише ті умови, які задав користувач, а значення передаються окремим списком параметрів.
- Список категорій у випадаючому меню формується запитом `SELECT DISTINCT category FROM products WHERE is_available = 1`.
- Якщо результатів немає, показується повідомлення «Нічого не знайдено». Є кнопка «Скинути» для очищення фільтрів.
- Значення в полях форми зберігаються після пошуку.

### 2.3. Адмінка товарів (`shop.admin_products`, адреса `/admin/products`)
| Дія | Маршрут | Метод | SQL |
|---|---|---|---|
| Список товарів | `/admin/products` | GET | `SELECT` |
| Додавання | `/admin/products/add` | POST | `INSERT` |
| Форма редагування | `/admin/products/<id>/edit` | GET | `SELECT ... WHERE id = ?` |
| Збереження змін | `/admin/products/<id>/edit` | POST | `UPDATE` |
| Перемикач доступності | `/admin/products/<id>/toggle` | POST | `UPDATE is_available` |
| Видалення | `/admin/products/<id>/delete` | POST | `DELETE` |

- Усі зміни даних виконуються методом POST (форма з кнопкою), а не посиланням, щоб їх не можна було викликати випадково чи через перехід за посиланням.
- Після кожної дії показується повідомлення через `flash(...)`.
- Адмінська сторінка наслідує `admin/base_admin.html` (блок `admin_content`), імена endpoint із заглушок не змінено.

### 2.4. Перевірка введених даних
- Назва товару не може бути порожньою.
- Ціна має бути числом не менше нуля (приймається і кома, і крапка; значення `NaN` та нескінченність відхиляються).
- При помилці форма повертається з уже введеними даними та повідомленнями про помилки.

### 2.5. Захист від видалення товару, що є в замовленнях
Таблиця `order_items` посилається на `products` із правилом `ON DELETE RESTRICT`. При спробі видалити товар, який є в замовленнях, база даних викликає `sqlite3.IntegrityError`. Я перехоплюю цю помилку й показую адміністратору підказку: вимкнути товар (перемикач доступності) замість видалення. Так історія замовлень лишається цілісною.

### 2.6. Безпека та правила роботи з БД
- Усі значення в SQL-запитах підставляються лише через `?` (жодних f-рядків).
- Читання виконується через `query_db`, зміни — через `execute_db` (вона сама викликає `commit()`).
- У шаблонах Jinja2 значення екрануються автоматично, що захищає від XSS.

### 2.7. Коміти та pull request
Робота виконана в окремій гілці, після завершення створено pull request у `main`, який зливає інший учасник команди. Історія комітів доступна в репозиторії на GitHub.

## 3. Схема бази даних
| Таблиця | Ключі | Призначення |
|---|---|---|
| `products` | PK `id` | товари: name, description, price, category, is_available |
| `customers` | PK `id`, UNIQUE `phone` | клієнти |
| `orders` | PK `id`, FK `customer_id` → `customers.id` | замовлення: статус, сума, дата |
| `order_items` | PK `id`, FK `order_id` → `orders.id` (ON DELETE CASCADE), FK `product_id` → `products.id` (ON DELETE RESTRICT) | позиції замовлення: quantity, price_at_order |
| `feedback` | PK `id` | відгуки користувачів |
| `promo_codes` | PK `id`, UNIQUE `code` | промокоди: discount_percent, is_active |

### Зв'язки
- `customers` 1 : N `orders` — один клієнт може мати багато замовлень.
- `orders` 1 : N `order_items` — замовлення складається з кількох позицій.
- `products` 1 : N `order_items` — один товар може бути в багатьох замовленнях.
- Отже, `orders` і `products` пов'язані «багато-до-багатьох» через проміжну таблицю `order_items`.

### Таблиця `products` (моя частина)
- `id` — первинний ключ, унікально ідентифікує товар; за ним працюють редагування, перемикання доступності та видалення.
- `name`, `description`, `price`, `category` — дані картки товару.
- `is_available` — ознака доступності (1 — показувати в меню, 0 — приховано).

Схема бази даних спільна для всієї команди, тому однакова в усіх звітах. Скриншоти адмін-панелі подано в звітах інших учасників команди.

## 5. Труднощі й рішення
- **Видалення товару, що є в замовленнях.** Зовнішній ключ `RESTRICT` не дозволяє видалити такий товар. Рішення: перехоплення `sqlite3.IntegrityError` і підказка вимкнути товар через `is_available`.
- **Безпека пошуку.** Текст пошуку не можна підставляти в запит через f-рядок (SQL-ін'єкція). Рішення: параметризований запит `LIKE ?` зі значенням `'%' + q + '%'`.
- **Заміна endpoint меню.** Перехід на `shop.menu` потребував узгодження зі спільними файлами (`base.html`, `app.py`) і попередження команди в чаті.
- **Поєднання пошуку та фільтра.** Запит формується динамічно: умови додаються лише за потреби, значення передаються окремим списком параметрів.
- **Залежність від частини А.** Кнопка «Додати в кошик» посилається на endpoint `cart.add_to_cart`, який реалізує інший учасник. Щоб сторінка меню не залежала від готовності кошика, посилання формується безпечно: якщо endpoint ще не підключений, використовується адреса `/cart/add/<id>`.

## 6. Відповіді на запитання до моєї частини
**Що таке первинний ключ і як він використовується в `products`?**
Первинний ключ — це поле (`id`), значення якого унікальне для кожного рядка й однозначно його ідентифікує. У `products` за `id` знаходять товар для редагування, перемикання доступності та видалення, а `order_items.product_id` посилається на нього як зовнішній ключ.

**Чому не можна підставляти текст пошуку в запит через f-рядок?**
Користувач може ввести фрагмент SQL-коду, який виконається як частина запиту (SQL-ін'єкція) і дозволить читати чи змінювати чужі дані. Параметризований запит (`?`) передає значення окремо від тексту запиту, тому воно завжди сприймається як дані, а не як команда.

**Навіщо потрібен RESTRICT?**
`ON DELETE RESTRICT` забороняє видаляти товар, на який посилаються рядки `order_items`. Це зберігає цілісність даних: історія замовлень не втрачає позицій. Замість видалення товар вимикають через `is_available`.

**Що таке CRUD і яким SQL-командам він відповідає?**
Create — `INSERT`, Read — `SELECT`, Update — `UPDATE`, Delete — `DELETE`. У моїй частині всі чотири операції реалізовано для товарів в адмінці.

**Чому видалення робиться через POST, а не посиланням?**
Посилання (GET) можна відкрити випадково, воно може бути виконане пошуковим роботом або попередньою загрузкою сторінки. Зміни даних мають виконуватися методом POST (форма з кнопкою).
